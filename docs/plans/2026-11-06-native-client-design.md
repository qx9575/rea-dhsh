# 新水浒Q传原生客户端复刻设计

- 日期：2026-11-06
- 状态：已与需求方逐节确认
- 首个里程碑：应天府单地图离线探索（Native Client M1）

## 1. 背景与目标

当前仓库是客户端逆向与资源工具箱，不是已有的客户端实现。现有成果包括：

- PAKF/NZ、APG/PIF、A16/CTI、地图、APCI 等资源格式解析与导出；
- `kimi_viewer` 直接读取原始 PAK、合成地图场景、播放纸娃娃动画；
- SCP 窗口树、include、脚本块和消息绑定解析；
- 网络传输加解密与部分消息语义研究。

复刻目标不是继续堆叠资源导出，而是建立可维护的原生客户端。原资源和 Lua 尽量原样使用，C++ 按原二进制证据逐项移植；不直接加载 `Game.exe`、保护组件或原保护 DLL。

### 1.1 复用边界

**原样复用：**

- Lua 源码、SCP 界面脚本、CSV/INI 配置；
- PAK 内图像、动画、地图、音频和字体；
- APCI/PIF 中的纸娃娃层叠、锚点、动作、方向和帧延时关系。

**按证据移植：**

- 动画加载、帧迭代、锚点与延时；
- 地图遮挡、深度排序和碰撞查询；
- 纸娃娃装配和层叠排序；
- SCP 解析、消息分发、Lua 绑定；
- 后续移动、寻路和角色状态机。

**不采用：**

- 把 Ghidra 伪代码当作可直接编译的完整 C++ 源码；
- 抽取并链接 `Game.exe` 内固定地址的机器码；
- 把原客户端及其保护、启动和更新环境作为新客户端运行时底座。

### 1.2 首版非目标

M1 不做登录认证、真实网络、切换地图、NPC 对话、战斗、任务、背包和存档。未实现的原界面按钮必须明确标记不可用，不伪造业务结果。

## 2. 技术路线与总体架构

采用 **C++20 + CMake + Win32/D3D11 + 与原客户端匹配的 Lua VM**。Lua 的精确兼容版本由现有样本和二进制证据确认后固定，不预先假定。

首版采用 CPU 合成画面，D3D11 只负责显示和窗口缩放。优先还原精灵 alpha、遮挡暗化和深度排序行为，避免 GPU 混合差异干扰正确性验证。原始逻辑分辨率为 800×600。

```text
Win32 应用壳 / 主循环 / 输入 / 音频
                  │
                  ▼
       场景、角色、移动、相机、UI 状态
                  │
          ┌───────┴────────┐
          ▼                ▼
   原生 2D 渲染器       Lua + SCP UI 运行时
          │                │
          └───────┬────────┘
                  ▼
       PAK / NZ / APG / MAP 等资源层
                  │
                  ▼
        只读访问 D:\software\dhsh
```

### 2.1 模块职责

- **资源层**：提供统一 `ResourceProvider`，逐步将现有 Python 解码器移植到 C++。能直读 PAK 的格式优先直读；暂未移植的格式可由 Python 生成运行缓存，通过同一接口加载。
- **渲染层**：只处理图像、锚点、帧延时、层级和遮罩，不直接理解 PAK。
- **场景层**：负责 MAP/MAN/CEL/MLK/core、角色、NPC、相机和点击移动。
- **脚本层**：嵌入 Lua，按需实现 `FSLua*` 宿主 API；SCP 生成原生控件，不改写成 Qt 界面。
- **本地状态层**：M1 使用本地角色与场景状态，不连接官方服务器。保留网络边界，但不在 M1 实现协议。
- **验证工具**：保留现有 Python 解码器和 `kimi_viewer` 作为参考实现，用于输出对照和定位 C++ 移植差异。

## 3. Native Client M1

M1 启动后直接进入应天府，不制作无实际功能的假登录页。

### 3.1 必须交付

- 原生窗口、800×600 逻辑画面、缩放与输入；
- 应天府背景、MAN 场景动画、地图音乐和 MLK 提供的合法出生点；
- 一个可选预设角色，使用原 APG/PIF/APCI 资源播放八方向待机和行走动画；
- 点击地面移动，使用 CEL 地面碰撞和 A* 寻路，角色沿路径平滑移动；
- 相机跟随、场景对象深度排序、建筑或树木遮挡时的 ghost 暗化；
- NPC 与场景动画正常播放；
- 加载原 SCP 主界面所需的控件子集；
- 至少打通一个“按钮消息 → 原 Lua 回调 → 窗口状态变化”的完整链路。

### 3.2 运行数据流

```text
启动
 → 建立只读 PAK 索引
 → 读取应天府 MAP / CEL / core / MAN / MLK
 → 创建角色、NPC 和场景对象
 → 输入 → 寻路/移动 → 动画与相机更新
 → 背景/对象/角色/UI 合成
 → D3D11 显示
```

### 3.3 验收方式

与 `map_preview.py`、`kimi_viewer` 和原客户端截图对拍，检查：

- 出生位置和地图图层；
- 角色锚点、动画方向与帧延时；
- CEL 碰撞和寻路结果；
- 深度排序与遮挡暗化；
- SCP 控件和 Lua 回调链路。

必须启动真正的原生客户端完成端到端验收，不能只靠单元测试或截图生成器判定完成。

## 4. 兼容与错误处理

- **资源访问只读**：PAK、字体和音频均从原目录读取；缓存与日志只写新工程目录。
- **格式防御性解析**：检查偏移、长度、帧数和递归层级，损坏资源不得导致越界或进程崩溃。
- **按资源隔离失败**：单个 NPC、动画或音效失败时记录逻辑路径与原因并跳过；地图背景、碰撞或角色核心资源失败则停止进入场景并给出明确错误。
- **缓存可更新**：转换缓存绑定来源文件大小、修改时间和内容摘要；客户端更新后自动失效，不混用新旧资源。
- **Lua/SCP 错误可定位**：日志包含 SCP 文件、窗口、控件、消息和 Lua 函数；不支持的控件或宿主 API 明确报告未实现，不静默成功。
- **路径兼容**：统一处理 PAK 内大小写与 `\`/`/` 差异，保留原始路径用于诊断。
- **无网络依赖**：M1 不读取账号、不连接原服务器，不依赖启动器和保护组件。

## 5. 测试与性能

- 每种 C++ 解码器使用真实 PAK 样本与 Python 参考实现对照；已位精确的格式要求输出一致，特殊 JPG 的既有误差单独记录。
- 地图测试覆盖已知坐标、CEL 越界/补齐规则、MAN 排序、core 遮挡和角色八方向动画。
- SCP/Lua 测试覆盖控件创建、消息注册、回调触发和脚本错误报告。
- 端到端测试覆盖启动、进入应天府、点击移动、阻挡、遮挡、动画和 UI 回调。
- 当前机器以 60 FPS 为优化目标并记录实际帧耗时；先保证正确性，再优化缓存和绘制热点，不把未测性能写成既成事实。

## 6. 实施顺序

1. **原生地基**：CMake、Win32 窗口、主循环、日志、资源定位与只读 PAK 索引。
2. **静态场景**：MAP、背景、CEL、MAN/core 数据进入 C++，正确画出应天府。
3. **动画与角色**：APG/PIF/APCI、NPC、角色锚点、方向和层叠。
4. **可玩探索**：A*、点击移动、相机跟随、深度排序和遮挡。
5. **原 UI 链路**：按需实现 SCP 控件、消息系统和最小 `FSLua*` API，不提前实现完整 Lua 兼容层。
6. **联调验收**：音频、错误处理、性能测量、真实 PAK 回归和原客户端对拍。

每一步保留可运行产物。私有格式尚未移植时，只允许通过统一资源接口使用缓存，不改变后续原生直读目标。

## 7. 路线取舍

- **选择 C++ 原生路线**：符合原客户端技术形态，便于按反汇编移植算法，并为后续完整 Lua 宿主与协议兼容保留空间。
- **不选择 Python + Qt 作为最终客户端**：其适合作为资源工具和快速验证环境，但不符合本次原生复刻目标。
- **不选择 Web/Electron**：需要重新适配资源、中文编码、动画和大地图，且引入额外技术栈。
- **不直接复用原机器码**：原二进制与固定地址、全局对象、初始化顺序及保护运行环境耦合，直接包装不利于离线运行与维护。
